    The six-turn loop

    Never jump to a PR. If the official page already covers it, stop. If docs and code disagree, code wins — and we say both.

    graph TD
  T1["1 · What is the hole?"] --> T2["2 · Pick Chat / Video / Feeds / Mod"]
  T2 --> T3["3 · Verify official docs"]
  T3 --> Covered{"Already on the page?"}
  Covered -->|Yes| Stop["Say so and stop"]
  Covered -->|No| T4["4 · Check the code"]
  T4 --> T5["5 · Show the patch · wait"]
  T5 -->|They say no| Hold["Do not open a PR"]
  T5 -->|They say yes| T6["6 · GitHub PR or Linear"]

    Turn 1 — the hole

    A customer question, a ticket dump, or a docs URL. If they paste a payload, use only what they pasted. No customer-app queries.

    Turn 2 — the product

    Chat, Video, Feeds, or Moderation. Run that playbook so the agent uses the right holes, not a generic guess.

    Turn 3 — verify docs

    Official getstream.io pages only. If it is already documented, say so and stop. Do not invent a gap.

    Turn 4 — check code

    Only if the page is missing or wrong. Cite the file. Code wins when the two disagree.

    Turn 5 — confirm

    One-sentence gap, docs URL, what the code does, the paragraph to add. Then: PR or Linear? Wait.

    Turn 6 — ship

    Prefer a GitHub PR. If there is no writable docs repo, open Linear with the same markdown. Slack note if connected.

    Gap 1 · empty text

    The first verified hole. Docs say text is optional. They do not say when empty is normal, that the default UI will not send it, or that two SDK ids are two messages.

    Docs say

    text is optional on send-message. No mention of empty twins, UI vs API, or {userId}-{uuid}.

    Code does

    The send payload allows empty. Android’s default composer does not. Two ids a few milliseconds apart are two sends, not one edit.

    The patch
    Empty text is normal for attachments, polls, location, or MML with no caption. A message with no text and no attachments is accepted by the API and not sent by default UI. A soft-delete keeps original text. Patch lives in proposed/chat-send-message-empty-text.md.

    Gap 2 · deleted user on UpdateChannel

    New, from a real group-chat ticket this week. GDPR docs say delete is async and that queryUsers hides the user. They do not say group memberships linger, or that cleaning them up with removeMembers is a 400.

    sequenceDiagram
  participant App
  participant API
  participant Task as DeleteUsers task
  App->>API: DeleteUsers
  API-->>App: 201 · deleted_at set · task id
  Note over API: Group memberships still present
  App->>API: UpdateChannel removeMembers
  API-->>App: 400 / code 4
  Task->>API: Strip memberships later

    Docs say

    Deleting users is asynchronous. queryUsers does not return deleted users. conversations: hard deletes 1:1 chats.

    Missing: the 400, the lingering group membership, no exception_fields, no include_deleted.

    Code does

    Marks deleted_at immediately, then publishes DeleteUsers on the lowest-priority queue. ValidateChannelMembers rejects any id with DeletedAt set — including removeMembers — before a leave message can be stored.

    InputError is code 4. Channel not found is 16. Request timeout is 48, not 23.

    What Support should tell the customer
    Poll GetTask. When it completes, skip removeMembers for that user. Treat 400 / code 4 whose message contains “deleted user” as skip, not retry. Retry 429, 408 / 48, and 5xx. An empty queryUsers is not proof the user was deleted.

    Patch: proposed/chat-update-channel-deleted-user.md — add under GDPR → Deleting users, cross-link from Channel Members. Do not name the customer in a public PR.
